# 복합 상품 진단 — 구현 규칙과 검증

## 기능

상품의 최신월(또는 질문에 지정한 월)과 **달력상 바로 전월**을 비교해 기회 상품 후보 또는 관리 필요 상품을 보여준다.

- “판매 추세로 볼 때 저평가된 상품은?” → **기회 상품 후보**
- “지금 주목해야 할 상품 3개 알려줘” → 최대 3개 기회 후보
- “주목하고 관리해야 할 상품은?” → 관리 필요 후보
- “광고비는 늘었는데 성과가 떨어진 상품은?” → 광고비 증가 **그리고 광고매출 감소**를 모두 만족하는 관리 후보
- “판매는 오르는데 광고를 덜 쓰고 있는 상품은?” → 매출 증가 **그리고 광고비 감소**를 모두 만족하는 기회 후보
- “광고비 대비 성과가 안 좋아지는 상품은?” → ROAS 하락 조건을 만족하는 관리 후보

지정한 표현은 D의 제한된 규칙 기반 분기가 해석한다. 숫자·순위·신호는 C의 pandas 계산으로 정하고, D가 고정 근거 문장으로 표시한다. **이 복합 진단 경로는 LLM을 호출하지 않는다.** 기존 단일 지표 질문의 LLM Planner와 근거 ID 기반 설명은 유지한다.

## 계산 규칙

| 구분 | 조건당 1점 | 후보 진입 조건 |
|---|---|---|
| 기회 (최대 4점) | 매출 증가 / 주문 또는 판매량 증가 / ROAS가 같은 플랫폼·자료 종류의 비교 가능 상품 중앙값 이상 / 매출 증가율 > 광고비 증가율 | 매출 증가 **및** 주문 또는 판매량 증가 필수 |
| 관리 (최대 5점) | 매출 감소 / 주문 또는 판매량 감소 / ROAS 하락 / 광고비 증가 + 광고매출 증감률 ≤ 0 / 환불률 상승 또는 구매전환율 하락 | 확인된 주의 조건 1개 이상 |

- 점수는 **확인된 신호 수**이고, `evaluated_rules`는 계산 가능한 조건 수다. 없는 지표에는 점수를 주지 않으며 실패값 0으로 채우지 않는다.
- 명시적인 질문 조건은 점수에만 반영하는 것이 아니라 **모두 만족해야 반환**한다. 예를 들어 ‘성과가 떨어진’은 광고매출 감소(< 0), ‘성과가 안 나는/부진한’은 광고매출 비증가(≤ 0)다.
- 기회 순서: 점수 내림차순 → 매출 증가율 내림차순 → ROAS 내림차순 → 최신 매출 내림차순 → 플랫폼·자료 구분·상품 ID 오름차순.
- 관리 순서: 점수 내림차순 → 매출 증감률 오름차순 → ROAS 증감 오름차순 → 최신 매출 내림차순 → 동일한 ID 기준. 계산 불가 정렬값은 뒤로 보낸다.
- 변화율은 전월 값이 양수일 때만 계산한다. 비율의 분모가 0 이하이면 `null`. 증감률/비율/비율 차이는 소수 1자리로 표시한다. 비율 차이는 반올림 전 값의 차이이며, 점수 비교는 표시되는 반올림 값 기준이다.
- ROAS 중앙값 모집단은 해당 기준 월과 전월에 모두 존재하는 같은 플랫폼·자료 종류 중 ROAS가 계산 가능한 상품이다. `benchmark_count`에 개수를 담는다. 상품이 1개뿐인 중앙값은 자기 값과 같으며 시장 전체 대비 우위를 뜻하지 않는다.
- 기본 최신월은 업로드 전체의 최신월이다. 해당 월에 없는 상품을 이전 월로 옮겨 진단하지 않는다.

## 원자료와 상품 식별

상품은 **플랫폼 + 자료 종류의 ID 체계 + 상품 ID**로 구분한다. 이름이 달라져도 동일 ID는 비교하며, 표시명은 최신월 이름이다. 같은 월에 이름이 여러 개이면 문자열순 첫 이름을 사용한다.

- 통합 템플릿: 파일의 판매·광고 지표를 사용한다.
- 쿠팡 판매/광고 내보내기: `옵션 ID`와 `광고집행 옵션ID`가 **문자열로 정확히 같은 경우만** 판매·광고 값을 연결한다. 다른 ID는 이름이 같아도 연결하지 않는다.
- 네이버 광고의 `소재` ID와 스마트스토어 `채널상품번호`는 별도 ID 체계로 유지한다. 우연히 문자열이 같아도 합치지 않는다.
- 템플릿과 실제 내보내기도 서로 다른 자료 구분으로 유지한다. 같은 내용을 두 번 업로드하면 중복 집계될 수 있으므로 파일 중복 제거를 보장하지 않는다.
- 스마트스토어의 전환율·환불률은 해당 판매 자료만 쓴다. ‘전체’ 요약 행은 상품 후보가 아니다.
- 같은 상품이 두 달 모두 있어야 비교한다. 신규 상품·기준 월에 사라진 상품·전월 누락은 임의 0으로 바꾸지 않는다.
- 기존 KPI 정규화는 호환성을 위해 그대로 유지한다. 진단은 `DataFrame.attrs`의 내부 출처 기록으로 파일에 없는 지표와 빈 셀/대시를 구분한다. **출처 기록은 API rows에 추가되지 않는다.** 정규화 이후 df가 변경돼 출처와 맞지 않으면 재분석을 안내한다.
- 직접 함수 호출로 만든 출처 기록 없는 df는 모든 전달 지표가 실제 관측값인 공통 행으로 취급한다. HTTP 경로는 항상 `normalize_files()`의 출처 기록을 사용한다.

## 기존 API 연결

기존 흐름 `create_analysis_plan → compare.run_plan → create_insight` 안에 분기를 추가했다. B 라우터, `AnalyzeResponse`, 기존 `AnalysisPlan` 지표/필드는 변경하지 않았다.

`insight.plan`의 새 내부 계획:

```json
{
  "analysis_type": "product_diagnosis",
  "diagnosis_intent": "attention",
  "limit": 5,
  "period": null,
  "required_conditions": ["ad_revenue_down", "ad_spend_up"]
}
```

`insight.answer`는 기존 `list[dict]`를 사용한다. 각 행에는 순위·플랫폼·상품 ID/이름·기준/비교월·자료 구분·점수·계산 가능 조건 수·현재 지표·증감·서버 `reason_codes`·ROAS 중앙값 근거가 있다. D는 순위 연속성, 점수/조건 일치, 기간과 숫자 유효성을 검증하고 문장을 생성한다. 모델이 이유나 수치를 새로 만들지 않는다.

기존 답 표에 진단용 열 이름과 핵심 열 선택만 추가했다. 계산되지 않는 열은 숨기고 자세한 이유는 기존 ‘근거’에 표시한다. 전용 카드·새 API 호출·화면 상태 변경은 없다.

## 제한과 실패 안내

- 최소 2개월, 정확히 기준 월과 전월이 필요하다. 7월+9월을 전월 비교로 쓰지 않는다.
- 3개월 이상 입력해도 현재 MVP는 기준 월과 전월만 비교한다. 연속 추세 판정/미래 예측은 하지 않는다.
- 조건에 맞는 후보가 없으면 `status=ok`, `answer=[]`로 설명한다.
- 기간 부족·동일 ID 없음·필수 지표 계산 불가·원자료 불일치는 `run_plan`의 `AppError`를 기존 라우터가 `unsupported_question` 안내로 바꾼다. KPI는 유지한다.
- 경쟁사·원가·마진·재고·광고 소재 원인·미래 예측은 계속 거절한다. 필터, 수치 임계값, 복수 기간 등 표현할 수 없는 추가 조건도 버리지 않고 안내한다.
- ‘기회 후보’는 시장가치 평가나 투자 권고가 아니다. 재고·마진·소재·실제 예산은 운영자가 별도 확인한다.
